## CMS Framework Notes

- Layers (README › Architecture: layers): platform ← framework ← app. The framework never imports project code; what it needs (db client, resource descriptors, the user/access tables, auth hooks) comes from `src/manifest.config.ts`, read only by `src/framework/runtime.ts`. Tables stay in `src/db/schema` (Studio parses and regenerates that folder); the config passes `authTables` and registers their types through `Register` in `@/framework/config`. The website builder (`src/framework/site`) is framework code too, so it never imports app code: pass project behaviour in through registration, config or props (e.g. `<SiteEditorProvider upload>`). Run `pnpm check:boundaries` after changing imports.
- Build CMS resources with `defineResource<TItem, TFormValues>`. Infer persisted row types from Drizzle (`typeof table.$inferSelect`); use a separate joined type only when a query returns related/computed data. Derive form values from the Zod schema.
- Resource data views have separate `overview` and `pickup` configs. Both support `dataTableColumns` and `dataListColumns`; provide the list columns wherever cards should be available. Table and list columns are merged by column ID, so keep IDs/fields aligned and retain relationship keys even when hidden.
- Forms use `FormConfig` sections with responsive `cols`, optional per-section `responsiveCols` breakpoints, and per-field `span`. `className` controls the form's width; avoid restrictive max-widths for long resource forms. Group related fields and use more columns for compact numeric fields.
- Relationship pickup fields use `resource`, `mapField`, and `targetField`; `embeddedField` can provide the selected relation immediately on detail forms, and `fillFields` can display or copy related values.
- `FormInput` converts non-empty number inputs to numbers and cleared inputs to empty strings; field validation errors are shown immediately. Normalize empty numeric input in resource schemas before number validation, and avoid `z.coerce.number()` when an empty value must not become zero. Numeric money fields may accept number input but should parse to strings for Drizzle numeric columns.
- Drizzle is configured with `casing: "snake_case"`; keep TypeScript property names camelCase and database column names snake_case.
- Extend the framework through `@/framework/extensions`, not ad-hoc render functions: `defineFieldComponent` (bound to one form value), `defineBlockComponent` (form section with the whole form), `defineDetailComponent` (detail slots/tabs), `defineOverviewComponent` (overview slots). Register them in `src/components/extensions/index.ts`; configs reference them as `{ type, props }` (or `def.with(props)`), with `props` validated by the zod schema that also describes their editor controls.
- Default data views are config, not code: `dataView.overview.defaultView`, `dataView.overview.navigationView` (embedded/relation lists) and `dataView.pickup.defaultView` set initial sorting, filters, pinning, column order and widths per grid/cards; column arrays (order, `size`, `hidden`, `navigationHidden`, `pickupHidden`) set the base layout.

## Website builder

- Public site pages are built from sections defined with `defineSection` from `@/framework/site` (one file per type in `src/components/extensions/sections`, registered in its `index.ts`; `pnpm manifest section <name>` scaffolds one). Render texts, lists and media with the primitives (`<Text>`, `<List>`, `<RemoveItem>`, `<AddItem>`, `<MediaEdit>`, `<EditOnly>`) so they stay editable on the page. Section files must stay importable on the server (no "use client"). Data from the database goes in a server loader (`sectionData<T>()` on the section plus `defineSectionLoader` in `src/components/extensions/sections/data.ts`). Blocks from shadcn/ui or other libraries become sections by turning their texts into `text()` fields rendered with `<Text>`. There are no starter sections or pages. Guide: README › Building the website.
- Site code by role: `src/components/extensions/` (sections, header/footer, collections — what a project configures), `src/components/site/` (shared site UI to restyle; `SiteHeaderSlot`/`SiteFooterSlot` load and render the header and footer), `src/components/site/internal/` (reads, cache tags, media upload, session, the editor preview frame — plumbing), `src/framework/site/` (the engine).
- Public site pages are static (refreshed on CMS save through tagged reads in `src/components/site/internal/cache.ts`). Don't read cookies, headers or the signed-in user in site layouts or content pages, and don't call `setRequestLocale`: `src/i18n/request.ts` reads the locale from `[locale]` through `next/root-params`; signed-in UI comes from `useSiteSession()`. Keep stored content shapes compatible when changing a section schema, and never rename a section's `type`. Page saves validate sections strictly; reading stays lenient.
- `drizzle-kit push` creates RLS policies without their USING condition. `pnpm manifest db` restores the website read policies (site_page, site_settings) afterwards and `pnpm manifest doctor` checks them.
